# Channel events — what fires when

**When to read this.** You see a `<channel>` tag and need to know what just happened; OR you are deciding a reaction policy; OR you are debugging why a cue never showed up; OR no events are arriving at all; OR you need the voice rules.

Channel events arrive **between turns** as `<channel source="voltras" event_type="…" slot="…" …>{json}</channel>`. Scalars are on the tag (meta); structured detail is in the JSON body, whose first key is always `summary`.

## Are events even arriving?

Push registers only when Claude Code was launched with `--channels plugin:voltras-channel@voltras-local` (the `scripts/voltra-pt` default). Any other form is skipped **silently**: no error, no log line, the MCP keeps working over polling. The server emitting does not prove the host is delivering.

Probe once per session if you have not seen a tag: `debug.push_test_channel`, read `nonce` off the tag, `debug.confirm_channel {nonce}`; `matchedProbe: true` proves delivery. If no tag arrives, you are on polling: `set.live_metrics` for rep counts, `timer.wait` for rests, `device.get_state` for everything else.

## `meta.slot` — always present

`primary` for single-device flows, `left` / `right` on a bilateral rig or a single device connected via a persisted binding. Bilateral streams interleave; filter on it. Events that are cross-slot by nature (`bilateral_divergence`, `deterministic_stop_unavailable` with several slots) carry `slot_id` / `partner_slot_id` instead.

`setting_coerced` and `weight_implied_mismatch` also carry `slot_id`, the originating slot, alongside the publisher's `slot`.

## Resources

Three slot-templated resources exist for a poll-style read: `voltra://device/{slot}/current`, `voltra://session/{slot}/active`, `voltra://set/{slot}/active`. The unslotted forms (`voltra://device/current` and so on) are aliases for the `primary` slot.

## Event inventory

The authoritative list is the set of publish sites in the server source; the generated push-events table on the docs site is a subset and is not guaranteed exhaustive. Checked against voltras-mcp main.

### Inside an active set

| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rep_finalized`                  | When the **next** rep begins, closing the prior one. **The final rep is published by the set close itself**, right before `set_ended`                                                                                                                                                                                | `set_id`, `rep_count`, `peak_concentric_velocity` (m/s), `peak_eccentric_velocity`, `weight_lbs`. Body: per-phase peak and mean velocity and duration, `peak_force`, `rom_m`, `tempo_ratio`, `set_context.rep_count_so_far`. Exception: an inactivity close drops its trailing in-progress rep and emits no extra event                                                                        |
| `set_target_reached`             | A `notifyOn` `rep_count_reached` trigger matched                                                                                                                                                                                                                                                                     | Advisory. "That's eight, let go when you're done"                                                                                                                                                                                                                                                                                                                                              |
| `velocity_loss_exceeded`         | A `notifyOn` `velocity_loss_exceeded` trigger matched                                                                                                                                                                                                                                                                | `velocity_loss_pct`, `threshold_pct`, `baseline_velocity`, `current_velocity` (m/s), `baseline_rep_number`, `rep_count_at_threshold`, `movement_class`, and which source the threshold came from (explicit `pct`, `intent`, or the plan). The baseline is the highest peak among ELIGIBLE reps; a positioning pull or a half-rep is excluded. **A fact about velocity, never an effort claim** |

### Set and session lifecycle

| Event                        | Fires                                                                                             | Meta / use                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set_started`                | `set.start` succeeded, **or the server auto-armed on the lifter's own reps (`auto_armed: true`)** | `set_id`, `session_id`, `weight_lbs`, `requested_mode`, `active_mode`, `set_purpose`, `movement_class`, and `lifter` only when someone other than the owner is lifting. Body has `previous_set_summary`. **On `auto_armed: true`, call `set.start {setPurpose, watch}` at once** to upgrade it                                                                                                                                                                                                                                                       |
| `set_updated`                | `set.start` upgraded an auto-armed set in place                                                   | The new `set_purpose` and watch state. Happens once per set                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `idle_rep_reclaimed`         | An auto-armed set adopted reps that an earlier idle report already counted                        | `count`, `set_id`, and `idle_rep_count`, the session's idle total after the reclaim. Resynchronize to it. The reps were not lost                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `set_ended`                  | Any close                                                                                         | `closed_by`: `device` / `tool` / `inactivity_timeout` / `disconnect` / `session_end` / `guided_load_exited`; `rep_count`, the whole set's duration, `partial_reason` when partial, the device's own rep count when known, `lifter` when not the owner. Body: full `reps` array and `vbt_summary` (`first_rep_v`, `peak_rep_v`, `peak_rep_number`, `last_rep_v`, `velocity_loss_pct`, `mean_velocity`), plus a rep-count disagreement block when counts differ. No `set.get` needed. The stored `reps` array is authoritative over the per-rep stream |
| `set_aborted_by_mode_revert` | `set.start` refused because the mode-revert guard latched                                         | `requested_mode`, `actual_mode`, `timestamp_ms`. The motor did not engage. Recovery in `07-recovery-and-escalation.md`                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `session_exercise_changed`   | `session.set_exercise` succeeded                                                                  | `session_id`, `exercise_id` / `exercise_name`; body has the previous pointer                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `weight_implied_mismatch`    | At set close, the force-implied weight disagrees with the header weight                           | `header_weight_lbs`, `implied_weight_lbs`, `mismatch_pct`, `slot_id`. Fires when the weight changed after `set.start` and on a weight change under tension that never applied. Advisory                                                                                                                                                                                                                                                                                                                                                              |
| `bilateral_divergence`       | Two opposite-slot closes were paired with different rep counts                                    | `slot_id`, `partner_slot_id`, `rep_count`, `partner_rep_count`, `rep_count_delta`, `weight_lbs`                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

`vbt_summary` takes `first_rep_v`, `peak_rep_v` and `mean_velocity` from the eligible reps, the same window the velocity-loss trigger uses. `last_rep_v` is always the set's actual final rep: a short or slow last rep is the fatigue signal itself.

There is **no** separate device-ended event. The generated push-events table still lists one; nothing publishes it. Every close is a `set_ended` with `closed_by`.

`set_purpose` is `working`, `warmup`, `probe` or `technique`. The older `is_warmup` boolean rides alongside for one more release. Read `set_purpose`.

### Setters

| Event             | Fires                                 | Meta / use                                                                                                                                                                                                                                                                                                         |
| ----------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `settings_update` | The device echoed a setting           | `changed_field`, `changed_value`. Verification aid; not for surfacing. Its arrival does not prove a weight change under tension applied                                                                                                                                                                            |
| `setting_coerced` | The echo differed from what you asked | `field`, `requested_value`, `device_value`, `coercion_delta`, `source_setter`, `slot_id`, plus `set_id` / `session_id` when a set is open. Eccentric needs 2 matching echoes; weight, chains, damper, assist fire at once. Don't retry; tell the user. Live-only: no stored record, so no report can list it later |

### Engagement

| Event               | Fires                              | Meta / use                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `guided_load_state` | Every guided-load phase transition | `phase` (`armed` / `countdown` / `engaging` / `active` / `timeout` / `exited` / `idle`), `outcome`, `countdown_remaining_ms` on countdown, `requested_target_lbs`, `set_id` / `session_id` when the auto-set exists. `armed` confirms nothing. `active` means the unit entered the mode, not that load is on. `timeout` means the poll window expired, usually because nobody extended the cable |

| ---------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `timer_complete` | A `timer.start` elapsed                                                                   | `timer_id`, `label`, `duration_ms`, `expected_at`                                                                                                                          |

### Voice

| Event                            | Fires                                                                                  | Meta / use                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `voice_input`                    | The listener transcribed an utterance addressed to the coach (wake phrase "hey coach") | `latency_ms`; body `transcript`. Treat as user input                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `voice_input_failed`             | Transcription failed                                                                   | Common in gym noise with two people talking. Ask the user to repeat or type                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `voice_command_applied`          | The local weight fast-path already changed the weight                                  | `slot`, `command`, `weight_lbs`, `applied: "true"`, `clamped` when a relative step hit the 5..200 bound; body `previous_lbs`, `transcript`. **The write already happened; do not call `device.set_weight`.** Verify with `get_state` if it matters                                                                                                                                                                                                                                          |
| `voice_command_rejected`         | A weight phrase was recognized but not applied                                         | `reason`: `ambiguous_slot`, `slot_not_connected`, `no_connected_slot`, `out_of_range` (5..200, refused not clamped), `unknown_current_weight`, `nothing_to_undo`, `set_failed`, `no_weight_context`. Arrives with the `voice_input`, so you can still act                                                                                                                                                                                                                                   |
| `deterministic_stop_triggered`   | A safety phrase ("stop", "unload", "cut the weight") unloaded a slot                   | One per unloaded slot: `slot`, `matched_phrase`, `predicate_reason` (`active_set` / `loaded`), `trigger` (`warranted` / `bilateral_sweep`), `set_id`. `unloaded` is `"true"` **only when the device reported the release**. Otherwise it is `unconfirmed`, the content carries `release: "unconfirmed"`, and the spoken reply is "Stopping. Check the cable, the weight may still be on." **Treat an unconfirmed cable as loaded**: `device.unload` again and confirm by eye (`07`, Mode H) |
| `deterministic_stop_unavailable` | A safety phrase matched but nothing was cut                                            | `reason`: `not_warranted` (nothing mid-set or loaded), `no_connected_slot`, `evaluate_failed`, `no_safety_context`; `unloaded: "false"`. Arrives with the `voice_input`. If the lifter is actually loaded, `device.unload` now                                                                                                                                                                                                                                                              |

The voice fast-path needs `system.listen_start`. Weight phrases it handles, wake phrase optional: absolute ("set it to 70", "70 pounds", "go to 65", "seventy"; a bare number counts only at 20 lb and above so rep counting cannot write a weight), relative ("up 10", "add five", "drop 5", "take off ten", "lighter" / "heavier" for 5 lb), cancel ("cancel", "never mind", "undo that"; one level deep per slot). Slot targeting: an explicit "left" / "right" wins; otherwise the slot with the most recent set, or the only connected one. Conversation about weight ("how much should I use") goes to `voice_input` as before.

### The voice rules

- A safety stop on a bilateral rig cuts **every connected slot**, not only the warranted one.
- **The mic is deaf while any line plays.** Every spoken cue, automatic or `system.speak`, mutes the listener for its whole playback (hard cap 8 s). Frames are discarded, not buffered, and an utterance already in progress is dropped. A "stop" said during a cue is lost **with no event at all** (VW-173, open).
- So: keep cues short. Keep `midSet` cues off. Never speak while you wait for a spoken reply. During a heavy or to-failure set, stay silent and have the lifter keep a hand near the stop.
- `system.speak` and the automatic cues share **one queue**. Lines no longer play over each other. A call may return late because it waited its turn. `interrupt: true` cuts the line playing, drops the waiting lines, and speaks now; a dropped line returns `ok: true, spoken: false`. Use it only when the new line makes the queued ones pointless ("Stop. Don't lift.").
- `server.health.voiceReady` false means speech will not transcribe at all. Say so before relying on voice.
- Call `system.listen_stop` yourself; a spoken request over a cue never arrives.

## How to react

### Surface every time

`set_target_reached`, `velocity_loss_exceeded`, `set_aborted_by_mode_revert`, `idle_timeout`, `connection_changed` on a state change, `setting_coerced`, `weight_implied_mismatch`, `bilateral_divergence`, `lease_lost`, `deterministic_stop_triggered` (and check `unloaded`), `deterministic_stop_unavailable`, `voice_command_applied`, `voice_command_rejected`, `guided_load_state` on `timeout`, `isometric_result`.

### Act on at once, say little

`set_started` with `auto_armed: true`: upgrade the set. `idle_rep_reclaimed`: fix your idle count.

### Surface conditionally

`rep_finalized` (only if the user asked for live cues or the rep was notable), `idle_rep_summary` (if it keeps coming with a session open), `voltras_available` (not mid-set), `session_exercise_changed` (confirm the label), `rest_status` at `final`, `velocity_loss_watch_suppressed` (once, so they know why no velocity cue will come).

### Mostly ignore

`set_started` from your own call (the tool return told you), `set_updated`, `settings_update` (verification only), `idle_rep`, `coach_line`, `timer_complete` for a timer you already cancelled.

### Bilateral demux

`left` and `right` are independent: separate sets, sessions, setters, coercion history. Report both or the one that just finished; never merge them into one number except through `bilateral_divergence`.

### Late `set_ended`

After a disconnect, inactivity, or `session.end`, a `set_ended` arrives without a `set.end` call. Clean up your bookkeeping and say what happened: "device closed the set," "no reps for 90 s, closed it," "lost the connection mid-set."

## Reading past events

Channel events are not retained on the model side. `debug.recent_events {types}` reads the server's diagnostic ring buffer, whose names differ from channel event names. `setting_coerced` is not in it; catch it inline. Do not quote low-level capture content anywhere.
